# Правила пошаговой разработки

Правила, по которым ведётся пошаговая разработка min-trello на основе архитектуры
(`docs/architecture/*.md`) и ADR (`docs/decisions/*.md`).

## Охват
- Frontend (React + Vite) — `03-frontend.md`
- Backend (NestJS + Prisma) — `04-backend.md`
- Database + seed — `05-database.md`
- Deploy (Docker Compose) — `07-infrastructure.md`
- Запуск и тестирование

## Требования к шагам
- Разбивка строго пошаговая; у шагов есть зависимости, поэтому «независимость» означает:
  **предыдущие шаги не сломаны**.
- Каждый шаг: тестируемый, валидируемый, проверяемый, с однозначным DoD.
- Порядок артефактов (schema-first): конфиги → `packages/shared` (типы и контракты) →
  схема БД/миграции → доменный API → realtime → seed → фичи → тесты → деплой.
  Фичи не начинаются раньше контрактов, иначе шаги переизобретают поля/коды.

## Размер и старт шага
- Один шаг = один PR = один логический результат (timebox ≤ 1.5 дня, иначе дробим).
- **Definition of Ready:** зависимости закрыты, их артефакты доступны.
- Шаг завершён, если: CI на `main` зелёный, тесты предыдущих шагов не сломаны без правок,
  откат выполняется одним действием.
- Откат БД — forward-fix миграцией (Prisma не делает авто-down), а не rollback.

## Формат шага
1. **Граф зависимостей** шагов (в `plan/README.md`).
2. Шаг описывается секциями (как в `plan/*.md`):
   **Цель**, **Артефакты**, **Зависимости**, **Definition of Ready**, **Действия**, **Тесты**,
   **Команда проверки**, **Ожидаемый результат (DoD)**, **Откат**, **Продолжение после паузы**,
   **Оценка**, **Commit**.
3. **Definition of Done** шага: что создано, **команда проверки**, **ожидаемый результат**.
   Без команды и результата шаг не считается готовым.

## Тесты
- **Unit:** backend — сервисы через мок-репозитории (DI); frontend — хуки/компоненты (Vitest).
- **Integration:** backend — supertest + тестовая БД (миграции применены, данные очищены).
- **E2E:** Playwright на seed-данных (логин, CRUD, drag&drop, фильтры, live-обновления).

**Тестовая инфраструктура:** тестовая БД, команда применения миграций,
очистка между тестами (truncate/транзакции), порог покрытия.

## История шагов
Каждый завершённый шаг фиксируется в `docs/progress.md`:
`дата | шаг | что сделано | как проверить | commit hash | статус`.

## Git-процесс
- Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, `test:`).
- Каждый шаг — отдельная ветка + PR; merge только при зелёном CI.

## Ревью (solo)
- PR + self-review чеклист: DoD выполнен, smoke пройден, CI зелёный, откат описан.

## Откат и блокеры
- Для каждого шага описан способ отката (revert коммита/миграции).
- Если шаг ломает предыдущий — это **блокер**: работа останавливается до устранения.

## Ручная валидация
Для UI-шагов — smoke-чеклист (что открыть, что нажать, что увидеть).

## Seed
- Идемпотентный (`upsert`) + команда полного сброса `db:reset`.
- Данные: **2 пользователя, у каждого по 3 доски × 20 задач (итого 120) в разных статусах**,
  с метками, дедлайнами, исполнителями и комментариями.

## Quality gates в CI (GitHub Actions)
`lint` + `format:check` + `typecheck` + `test` + **сборка Docker-образов**
(обязательна, иначе не проверить `docker compose up`).

## Versioning контрактов
Меняешь API/схему — в том же шаге обновляешь `06-api.md`/`05-database.md` и ADR.

## Нефункциональные требования
- Seed-данные: приложение стартует с реалистичным демо-набором.
- Всё приложение поднимается одной командой `docker compose up` (backend + frontend + БД; Redis внутри).
- `README.md` (markdown) с инструкцией по запуску и тестированию.

## DoD финального шага
Чистый клон → `docker compose up` → health OK → логин seed-юзером → README проверен.
