# ADR-009: Конкурентные переносы карточек (advisory-локи + retry)

**Статус:** Принято  
**Дата:** 2026-09-25

## Контекст

`PATCH /api/cards/:id/move` выполняет двухфазную перенормировку `order` затронутых колонок
в интерактивной транзакции (READ COMMITTED). Живой прогон показал: 6 параллельных переносов
в одну колонку давали `200,500,500,500,500,200` — две транзакции обновляли одни и те же
строки `Card` в разном порядке и упирались в дедлок PostgreSQL (`deadlock_timeout` 1s
объясняет латентность ~2s), Prisma отдавал P2034 без ретраев, пользователь видел 500 и
откат optimistic-обновления. Для приложения с live-обновлениями (Socket.IO) параллельные
переносы — штатный сценарий, а не исключение.

## Решение

Три уровня защиты в `PrismaCardRepository.move`:

1. **Advisory-локи PostgreSQL** — `pg_advisory_xact_lock(hashtextextended(columnId, 0))`
   по затронутым колонкам (исходная + целевая) в лексикографически отсортированном порядке:
   единый порядок захвата исключает дедлок. Лок транзакционный (снимается автоматически),
   вызов реентерабелен. Карточка перечитывается под локами — если конкурентный перенос
   увёл её в третью колонку, лок на неё дозахватывается.
2. **Bulk-перенормировка** — каждая фаза (сдвиг в «хвост», финальный `0..n-1`) это один
   `UPDATE ... FROM (VALUES ...)` вместо 2N построчных апдейтов: короче удержание блокировок.
3. **Retry** — остаточные конфликты записи (P2034, PG 40P01/40001 — детектор
   `isWriteConflictError` в `common/prisma-errors.ts`) ретраются до 3 попыток с джиттером
   50–150 мс. После исчерпания `CardsService` отвечает `409 CONFLICT` — фронт откатывает
   optimistic-обновление и показывает баннер (готовый путь обработки).

Дополнительно `AllExceptionsFilter` теперь логирует имя и код исходной ошибки 5xx со стеком —
первопричина (дедлок) больше не маскируется строкой «Internal server error».

## Последствия

- Переносы одной колонки сериализуются: латентность растёт на миллисекунды вместо секунд
  ожидания `deadlock_timeout`.
- Коллизии `hashtextextended` между разными колонками безвредны — редкая ложная сериализация.
- `pg_advisory_xact_lock` возвращает `void`, не десериализуемый Prisma — используется
  `SELECT (... IS NULL)::int` (см. `lockColumn`).
- Семантика конкурентности остаётся last-write-wins; транзакции гарантируют уникальность
  и непрерывность `order` в каждой колонке.
- Контракт репозитория `ICardRepository` не изменился — юнит-тесты сервисов не затронуты.

## Альтернативы

- **Только retry без локов** — rejected: каждая попытка после `deadlock_timeout` (1s)
  даёт длинные хвосты латентности; лок устраняет причину, retry — страховка.
- **`SELECT ... FOR UPDATE` по строкам колонки** — rejected: не устраняет дедлок
  (порядок захвата строк при разных планах всё равно различается).
- **Serializable isolation** — rejected: больше конфликтов и ретраев при той же причине.
- **Дробный `order` / lexorank** — rejected: требует миграции данных и усложнения ради
  проблемы, решаемой локами на текущем масштабе.
